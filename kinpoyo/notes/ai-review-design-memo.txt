AIレビュー機能 設計メモ（2026-08-21 時点の相談内容）
====================================================

前提
----
- 対象：AI回数カウント機能が完成した後に着手する予定の「AIレビュー」機能
- ゴール：フォーム計測から得られた数値をもとに、Claude APIでトレーナー風のレビュー文章を生成する
- 現時点ではまだ実装していない。設計の方向性だけ相談・合意した内容のメモ。

基本方針：「判定」と「文章生成」を分離する
----------------------------------------
- 数値の閾値判定（深さが浅い／テンポが速すぎる、など）はAIに任せず、決定的なロジックで行う
  → 誤判定・ブレが起きない
- AIには「この観点についてコーチっぽく自然な文章にする」という、LLMが得意な仕事だけをやらせる
- 判定基準は新たに考案せず、model-studio較正済みモデルの cycleStats
  （bottomDeg / topDeg / romDeg などの実測範囲）を流用できないか検討する

プロンプト構成：ベース＋パーツ差し替え方式
------------------------------------------
検討の変遷：
  1案（フル差し替え）：観点の組み合わせごとに完成プロンプトをID管理
     → 共通部分（人格設定・出力フォーマット指示等）を全パターン分コピーすることになり、
       文言修正のたびに全部直す必要が出る。組み合わせ爆発しやすい。
  2案（パーツ差し替え・採用の方向）：
     - ベースプロンプトは固定・共通（1箇所）
     - 観点ごとに「差し替えパーツ（プロンプト断片）」をIDで管理
     - 実測値から該当する観点を複数拾い、該当パーツを組み合わせてベースに差し込む
     - 複数の問題が同時に起きるケース（例：深さが浅い×テンポが速い）でも、
       パーツを複数選んで結合するだけで対応でき、組み合わせの数だけIDを
       用意する必要がない

イメージ：
  ベースプロンプト（固定・共通）
    「あなたはAIパーソナルトレーナーです。以下の観点についてコメントしてください：
     {{差し替えパーツ}}
     実測値：{{実測値}}」

  差し替えパーツ（観点ごとにID管理）
    id=squat_depth_shallow : 「深さが目標より浅い傾向について、改善のアドバイスを」
    id=squat_tempo_fast    : 「動作が速すぎる傾向について、コントロールの重要性を」

重要な注意点
------------
1. 「登録されているプロンプト」は雛形（テンプレート）であるべきで、完成文そのものを
   IDで引いて返すだけにしない。
   → 完成文を返すだけなら固定メッセージ表示と同じでAIを使う意味がない。
   → プロンプト雛形＋実測値（ROM○°、目標との差○°、左右差○°など）をAIに渡し、
     その場で自然な文章を生成させる設計にする。

2. IDの粒度に注意する。
   → 種目×問題パターン×深刻度、と掛け算すると組み合わせ爆発しやすい。
   → 最初は種目ごとに3〜5個程度の主要な観点（深さ・テンポ・左右差・一貫性など）に
     絞るのが現実的。
   → 閾値のすぐ隣で全く違う文章になる「境界のジャンプ」にも気をつける。

3. AI処理テーブルとの関係（★要調整）
   → backend-core/app/models/workout.py の `ai_reviews` テーブルは、AGENTS.mdで
     「Claude API連携担当者が設計中のため変更禁止」と明記されている。
   → 差し替えパーツを保存する新規テーブルも、`ai_reviews` と同じ「AI処理」領域に
     隣接する内容のため、着手前に必ずその担当者と設計をすり合わせる必要がある。
   → 回数カウント機能の`rep_count_models`テーブルは無関係の別テーブルなので、
     このルールには抵触していない（このメモの対象であるAIレビュー機能が抵触する）。

次にAIレビューへ着手する際にやること（メモ）
--------------------------------------------
- Claude API担当者と、ai_reviewsテーブル・プロンプト設計をすり合わせる
- 判定ロジック（観点の閾値）をmodel-studioのcycleStats等から具体化する
- ベースプロンプト・パーツプロンプトの雛形を実際に書き起こし、実測値の埋め込み方を決める
- パーツ管理をDBテーブルにするかコード内定数にするか決める
