カウント判定のロジック（確定版）
--------------------------------
「流れに沿って追従し、**連続して**外れたらノーカン。ただし緩く運用する」。

  アンカー : 立位帯（実測トップ±20°）から5°以上・3サンプル連続の下降で追従開始
             → 座った状態から始まる動作を最初から拾わない
  追従     : 期待カーブ（較正テンプレートを絶対角度に戻したもの）に対する
             位相の進み方を監視
  ノーカン : 位相が進まない状態が 0.4秒 続いたら（= STALLED）
  完了     : ボトムを通過して立位帯に戻った時点で1回確定
  ガード   : ROM 40〜95°、テンポ 基準周期の0.4〜2.5倍、タイムアウト10秒

「緩く」の効かせどころ:
  - ROMは**非対称**。下限40°で緩く（浅いレップ・ハーフレップを拾う）、
    上限95°で締める（椅子に座る・床の物を拾う動作を弾く。実測ROMは68.6〜75.2°）
  - ノーカンは連続停滞のみ。流れに戻ったら即ゼロリセット（減衰させない）
  - 深さのズレはカウント可否に使わない。form_quality のラベルに回すだけ

しきい値は全て**秒**で持つ
--------------------------
バッチ版の minPeriodFrames / maxGapFrames / minSegmentFrames はフレーム数ベース。
動画は fps が固定なので成立していたが、リアルタイムは端末のフレームレートが可変。
フレーム数で持つと状況によって閾値の意味が変わるため、秒で持つ。

実装中に判明した重要なこと（★次に触る人はここを読む）
------------------------------------------------------
1. **「許容倍率の包絡線をコリドーにする」方式は機能しない。**
   時間方向の伸縮を許すため、較正基準周期の0.4〜2.5倍に対応する位相区間の期待角度
   の包絡線をコリドーにしようとした。→ 許容が6.25倍幅もあるため、レップ開始直後に
   カーブ全域を覆ってしまい、合成信号の**全ケースで逸脱0.0°**になった。制約として
   何も働いていない。

2. **「序盤でテンポ倍率を1つ確定させる」方式は、深さとテンポが結合して破綻する。**
   絶対角度から位相を逆引きすると、較正より深いレップは「同じ時刻でより先の位相に
   いる」ように見えるため、テンポ倍率が systematically 過小に確定する。結果、
   期待スケジュールが早く終わり、まだ上がっている途中で「期待は既にトップ」となって
   正常なレップがノーカンになった（ROM 78°・3.0秒のレップで再現）。

3. **角度そのものの許容帯は要らなかった。**
   単調区間では角度から位相が一意に決まるため、角度単体では定義上ほぼ外れようがない。
   深さのズレを見る役割は ROM ガードと二重になるだけだった。

   → 1〜3を経て、最終的に観測軸を**位相の進み方（停滞しているか）**にした。
     テンポにも深さにも依存しない指標なので、ゆっくりな人・深い人を巻き込まない。

4. **単発ノイズ対策には EMA だけでは足りない。3点メディアンが要る。**
   EMA は外れ値を薄めるだけで残すため、位相の逆引きが汚れる。±18°のスパイクを
   3フレームおきに入れると全レップが落ちた。因果的な3点メディアン（1サンプルの
   群遅延と引き換えに単発外れ値を完全除去）を EMA の前段に入れて解消。
   バッチ版の `_declitch()` + `_smooth()` に対応するが、どちらも未来フレームを
   参照する実装なので流用はできない。

5. **「即ノーカン」の判定パスは連続逸脱の保護を迂回する。**
   4のノイズ全滅は、テンポ倍率の確定が1サンプルの単発判断で、かつ「テンポ許容外」を
   連続逸脱を待たず即ノーカンにしていたことが原因だった。単発判断で確定させる値を
   作るときは、必ず複数サンプルの中央値等でロバストにすること。

6. **cycleStats は閾値にそのまま使えない。**
   `build_cycle_stats()` は実測レンジに余裕幅（±25° or ±35°）を足した「ゲート用の帯」
   を保存しており、実測値そのものは保存していない。リアルタイムの基準には実測値が
   要るので、`derive_raw_cycle_stats()` で余裕幅を逆算している。定数が途中で緩められて
   いる（25.0/(0.5,2.0) → 35.0/(0.4,2.5)）ため、どちらで作られたモデルかを整合性
   （min <= max が成り立つか）で判別する。
   → 恒久対応：**再較正時に実測値を `cycleStatsRaw` として保存すること。**

較正データの実態（2026-08-27 時点・要注意）
-------------------------------------------
model-studio 本番API の model id=15（スクワット、2026-07-14生成）を確認した結果：

  mae = 0.0 / 完全一致率 = 100%  ← ただし **session_count = 2 / cycleCount = 2**
  poseSpace = world
  shapeThreshold = 0.35          ← 旧計算式（max*1.5・下限0.35）の産物
  cycleStats: bottomDeg [60.7, 111.6] / topDeg [130.2, 185.9] / romDeg [34.3, 150.4]

- mae=0.0 は「2セッションで学習して同じ2セッションで評価した値」であり、汎化性能の
  証拠ではない。
- topDeg の上限 185.9° は関節角度の物理上限180°を超えており、上側のゲートは
  事実上何も弾いていない。romDeg 34〜150° も同様。
- 逆算した実測値：
      サイクルA: ボトム 86.6° / トップ 155.2° / ROM 68.6°
      サイクルB: ボトム 85.7° / トップ 160.9° / ROM 75.2°
- テンプレートの std は 0.002〜0.045。2サイクルしかないため異常に狭く、許容帯の
  算出には使えない（固定幅で持つ理由）。

★ RealtimeConfig の初期値は全て暫定。「本物のレップがどれだけばらつくか」が
  分からないと決められないため、**較正動画を2本から10〜20本に増やしてから
  実データで詰め直すこと。**

AIレビューへの影響（要対応）
----------------------------
ノーカンを持つ以上、2026-08-24 に決めた「カウントと評価の分離」と再び交差する。

- `rep_cycles_json` の `counted=false` は現在「点数不足で測定不能」＝データ有効性の
  問題のみを指す。ここにフォーム逸脱によるノーカンが混ざる。
- `review_judge.aggregate_cycles()` は `counted=true` だけを集計するため、ノーカン分は
  AIレビューの母数から消える（「10回やったのにレビューが7回分で語る」状態）。

→ 対応方針：`RepEvent.not_counted_reason`（stalled / tempo_out_of_range /
  rom_out_of_range / timeout / pose_lost）を `rep_cycles_json` にも持たせ、
  AIレビューには「流れから外れて数えなかったレップがN回」を実測値として渡す。
  数えないが、無かったことにはしない。**スキーマ変更は未実施。**

2026-08-28 追記：腕立て伏せのモデルを紐づけて判明した欠陥
----------------------------------------------------------
プッシュアップ（exercise_id=4、model-studio の tag_id=18「腕立て（アレックス）」、
model_id=16、セッション7本）を取り込んだところ、**スクワット1種目では露見しなかった
欠陥が2つ**出た。種目が増えて初めて分かる類のもの。

【欠陥1】ボトム付近で正常なレップが「停滞」と誤判定される
  腕立てのテンプレートはボトム付近が平坦（押し切った位置で溜める）。角度がほとんど
  変わらないぶん位相の逆引きが進まず、ゆっくりしたレップが stalled で落ちた。
  → 較正ROMの70%以上まで沈んでいれば停滞検知を止める（stall_exempt_descent_ratio）。
    ボトムでの溜めはフォームであって流れから外れたわけではない。

  ※ 除外条件を「テンプレートのボトム位相への近さ」で書くと**浅いレップを救えない**。
    浅いレップは自分の折り返しがテンプレートのボトム位相より手前に来るため。
    「自分がどれだけ沈んだか」で判定すること。

【欠陥2】立位帯（±20°固定）がROMの小さい種目に対して広すぎる
  腕立てのROMは57.6°なので、20°はROMの35%に相当する。途中で止まってノーカンに
  なった後、その位置（まだ3分の1しか沈んでいない扱い）から再アンカーして浅いレップを
  1回数えてしまった。
  → 立位帯を較正ROMの20%で頭打ちにする（anchor_top_tolerance_rom_ratio）。

【判明した原理的な限界】「途中で止まった」と「ボトムで溜めた」は区別できない
  実測値:
      スクワット  tau=0.3 での停止 → 沈み込み 79.6%
      腕立て      浅いレップのボトム → 沈み込み 79.2%
  **スクワットの「途中停止」の方が腕立ての「浅いレップのボトム」より深い。**
  したがって沈み込み量だけで両者を分ける閾値は種目横断では存在しない。因果的な情報
  （未来を見ない）だけでは原理的に区別不能。

  → 割り切り：**浅い段階での停止だけを「流れから外れた」とする。** 深く沈んだ位置
    での溜めは正当なフォームとして通す。長く止まりすぎたレップはテンポ上限
    （基準周期の2.5倍）が受け持つ。合成テストの期待値もこれに合わせて修正した
    （「序盤で1.5秒停止」=ノーカン / 「ボトムで1.5秒溜める」=カウント）。

複数種目が揃ったことで顕在化する既知の制約
--------------------------------------------
`frontend/app/(tabs)/workout.tsx` の `findAiReadyExercise()` は、セッションの種目を
先頭から探して**最初に見つかった1件でreturnする**。較正済み種目が1つだった間は
問題にならなかったが、スクワットと腕立ての両方を含むメニューでは**片方しかカメラが
起動しない**。AGENTS.md の既知制約そのもので、未対応のまま。
