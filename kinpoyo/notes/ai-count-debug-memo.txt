AI回数カウント機能 デバッグ記録（2026-08-22〜08-24）
====================================================

前提・症状
----------
- config（rep_count_models.config_json）・アルゴリズム（rep_model.py）・mediapipeバージョンを
  model-studioと完全に一致させたはずなのに、同じ動画を処理しても
  kinpoyo側は毎回カウント0（統計ゲートで棄却）、model-studio側は正しく3回カウントされる、
  という現象が数日がかりの調査になった。
- 最終的な原因はたった1箇所、MediaPipeのランドマークの種類の取り違えだった。
  結果から見ると小さなミスだが、そこに辿り着くまでに非常に多くの回り道をした。

最終的な原因（結論）
--------------------
backend-core/app/core/pose.py で、MediaPipeの検出結果から

    result.pose_landmarks       ← 画像正規化座標（誤り。これを使っていた）

ではなく

    result.pose_world_landmarks ← 実世界3Dメートル座標、腰が原点（正解）

を使うべきだった。

なぜ結果が変わるか：
- pose_landmarks は x が画像の幅、y が画像の高さでそれぞれ別々に正規化されており、
  アスペクト比の分だけ歪む。z もx/yとは全く別スケール。
  この3つを混ぜて内積計算すると、カメラの位置や動画のサイズに依存した無意味な角度になる。
- pose_world_landmarks はメートル単位の実3D座標なので、3点で決まる角度は
  座標系の回転・平行移動に対して不変（＝カメラをどこに置いても同じ値になる）。
- model-studioの角度計算コード（pose_analysis.py）には、まさにこの注意書きが
  コメントとして書かれていた。ただし「ローカルのmodel-studioリポジトリの
  pose_analysis.py」には書かれておらず、Azureに実際にデプロイされているコードにのみ
  存在した（ローカルとAzureのファイルがズレていた。詳細は下記）。

やったこと（時系列・回り道の記録）
------------------------------------
1. 500エラー（UnicodeEncodeError / PermissionError）
   → stdout/stderrをUTF-8化、cap.release()の try/finally 漏れを修正。これは正しい対応だった。

2. 「MediaPipeのTasks API（新）と legacy API（mp.solutions.pose、旧）はモデルの中身が別物では」
   と疑い、Python 3.14→3.12化、mediapipeをlegacy APIが動くバージョン範囲
   （0.10.14〜0.10.21）に切り替え。
   → 結果は変わらず。ただし後から振り返ると、これ自体はmodel-studioと環境を揃える
     正しい判断だった（無駄ではなかったが、根本原因ではなかった）。

3. プロジェクトパスの日本語（HAL名古屋）によるMediaPipeの非ASCIIパス問題
   → venvをASCIIパスの場所（C:\venvs\...）に作り直して回避。これも正しい対応。

4. 動画の回転（縦撮り動画が横倒しのままMediaPipeに渡っている？）を疑う
   → 実際に1本、回転メタデータを無視されている動画があり、これは本物のバグだった
     （CAP_PROP_ORIENTATION_AUTOの有無で直った）。ただし本題の「model-studioとの
     数値の不一致」の原因ではなかった＝別の本物のバグに気を取られた形。

5. OpenCVのバージョン差（4.x vs 5.x）を疑い、Azureとバージョンを合わせる
   → 変化なし。

6. numpyのバージョン差を疑い確認
   → ほぼ同じバージョンで、原因ではなかった。

7. サーバーの起動方式（uvicorn --reload vs gunicorn+UvicornWorker）を疑い、
   Docker上でgunicornに揃えて再現
   → 変化なし。

8. 生のランドマーク座標をAzureのSSHコンソールで直接ダンプして比較
   → 1回目は検証スクリプト自体にバグがあり（frame間を飛ばして pose.process() を
     呼んでいたため static_image_mode=False の連続追跡が壊れていた）誤った
     「一致している」という結論を出してしまった。全フレーム連続処理に直して
     再検証したところ、実は数値が一致していた（この時点では pose_landmarks 同士の比較）。

9. 「それなら本番APIのレスポンス自体がおかしいのでは」と考え、model-studioの
   本番API（/models/{id}/count）に直接同じ動画ファイルを送って確認
   → 本番APIは正しく「3回・ROM82°」を返した。SSHでの手動スクリプトの結果と
     本番APIの結果が食い違う、という新たな謎が発生。

10. 本番エンドポイントのコード（ファイルコピー→再オープン、ORIENTATION_AUTO、
    POS_FRAMES(0)シーク、async実行）を1つずつ手動スクリプトで再現して切り分け
    → 全部再現しても変わらず。

11. 最後の手段として「ローカルのmodel-studioリポジトリのファイルと、
    Azureに実際にデプロイされているファイルのmd5ハッシュを比較」
    → main.py・rep_model.py・pose_analysis.py のハッシュが不一致（pose.pyだけ一致）。
    ここでようやく「参照していたローカルコードが古い（デプロイ後に更新されていた）」
    と判明。Azure側の pose_analysis.py の中身を直接catしてもらったところ、
    pose_world_landmarksを使うべきというコメントが書かれていた。
    → 修正して即座に一致（3回・ROM81.7°）。

最初からやるべきだったこと（次回への教訓）
--------------------------------------------
1. 「ローカルのmodel-studioリポジトリ＝Azureに実際にデプロイされているコード」
   という前提を無条件に信じてしまった。
   → deploy.ps1 は手動zipデプロイ方式で、ローカル変更後にデプロイし忘れる／
     Azure側だけ更新される、という乖離が起き得る構成。
   → 「model-studio変更禁止」というルールは「ローカルのファイルを読んで移植すれば
     Azureと同じ結果になる」ことを保証しない。数値が食い違った時点で、真っ先に
     ローカルファイルとAzure実機のmd5ハッシュを比較するべきだった
     （実際にやったのは調査のほぼ最後）。

2. MediaPipeには pose_landmarks（画像正規化座標）と pose_world_landmarks
   （実世界3D座標）の2種類があることを、そもそも最初に確認するべきだった。
   → model-studioのローカルコードは pose_landmarks を使っていたため、
     「これに合わせれば正しい」と思い込んでしまった。もし最初に
     「MediaPipeのPose、image座標とworld座標の違い」を調べていれば、
     角度計算にはworld座標を使うべきという一般的な注意点にすぐ気づけたはず。
   → 特に、奥行き方向（しゃがみ込みのような動き）を含む角度は、画像正規化座標では
     カメラ距離・アスペクト比の影響を強く受けるため、そもそも不向き。

3. 「環境（バージョン・OS・サーバー起動方式）を1つずつ揃えていく」というアプローチは、
   一致しない原因が「コードの中身の違い」であるケースには効かない。
   → 環境を疑う前に、まず「本当に同じコードを見ているか」（ファイルのハッシュ比較）を
     最初に確認するべきだった。これを最初にやっていれば、6〜10の回り道
     （OpenCV/numpy/gunicorn/async等の切り分け）は不要だった可能性が高い。

4. 生データ（ランドマーク座標）の比較検証をするときは、MediaPipeの
   static_image_mode=False（連続追跡）を使う場合、検証用スクリプトでも
   「全フレームを順番に pose.process() へ通す」ことを徹底する。
   一部フレームだけ間引いて処理すると、追跡状態が壊れて別物の結果になる
   （8番の回り道で実際に踏んだ）。

5. 「同じに見える動画ファイル」（フレーム数・fpsが同じ）でも、由来が違えば
   別バイト列の可能性がある、という疑いは早い段階で持つべきだったが、
   今回は逆に「本当に同じファイルか」を疑いすぎて時間を使った側面もある。
   最終的には「同じファイルのmd5を両方で取って確認する」のが一番早い確認方法。
